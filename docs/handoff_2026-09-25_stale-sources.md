# Хендоф 25.09.2026 — «57 молчащих источников»: корень по группам

Ветка `fix/stale-sources-0925`, PR electromop/oiltech-digest#69. Метод — `/diagnosing-bugs`: сначала проба, которая
краснеет на симптоме, потом гипотезы. Всё на проде — только чтение (кроме инцидента ниже).

## Итог в одном абзаце

«Синхронный обрыв 18–19.09» — в основном **не поломка, а артефакт**: 18.09 новые правила порядка
ссылок (2bac79c) дали разовый пересбор, и у ~38 редко пишущих источников в базу легло старьё и
навигация. На три дня они стали «свежими» (19.09 stale = 19), а 21–22.09 разом стали stale (25.09 — 57).
Настоящие потери нашлись поштучно, и главная из них системная: **ключ адреса 13.09 срезал query
целиком** и склеил все статьи сайтов, где номер статьи в query (Минэнерго, EIA, РГУ Губкина, Новатэк,
Лукойл, Anton Oil, ONGC). С 13.09 каждая их новая статья молча отбивалась как «дубль», а схема 13.09
ещё и спрятала уже собранные. Это исправлено в ветке, восстановление спрятанного — отдельной командой.
Остальные потери точечные (извлечение/предфильтр/порядок у конкретных сайтов) — описаны ниже,
в код не вносились.

## Проба — чем мерили

Путь сбора (`fetch` → `extract_candidate_links` / `extract_articles_from_feed` → статья → предфильтр),
но вместо `insert_article` — три его рубежа SELECT-ами и вердикт по каждому кандидату: `known` (адрес
уже в базе), `TOO_SHORT`, `PREFILTER`, `DUP_URL_KEY_SAME` (та же статья), `DUP_URL_KEY_OTHER` (склеена
с ДРУГОЙ статьёй — потеря), `DUP_BODY_HASH` (то же тело, что у статьи источника), `WOULD_INSERT`.
Плюс кандидаты за лимитом 12: позиция на странице и дата самой статьи — «свежее, но спрятано порядком»
против «старьё/навигация». Запуск на ядре: `docker exec -i oiltech_scheduler python - < probe.py`,
соединение в режиме `READ ONLY`. Различитель `SAME`/`OTHER` обязателен: без него «дубль по ключу»
выглядит одинаково для нормы и для потери. Скрипт был одноразовым и в репозиторий не вошёл (не
просили); его место — вердикты рубежей вставки в `source-diagnose`, которому их сейчас не хватает.

## Выкат и восстановление — только после «да» владельца

1. Выкат ядра, по одному и не во время чужого выката: `cd /root/oiltech-digest && sh scripts/deploy-core.sh
   --no-schema app scheduler worker playwright-worker`. `--no-schema`: в `schema.sql` поменялся только
   бэкфилл строк без ключа, таких на проде нет. `insert_article` работает и в планировщике, и в приложении
   (итоги NL-воркера), поэтому оба.
2. Сразу после — сухой прогон: `docker compose run --rm --no-deps -T app python -m oiltech_digest.cli
   repair-url-keys`. Ожидание по сухому прогону 25.09 07:11 UTC (логика после ревью на данных прода,
   READ ONLY): **вернуть 308** (Губкин 177, Минэнерго 69, EIA 40, Новатэк 10, Anton 6, Лукойл 5,
   ONGC 1), ключей пересчитать 725, дублей в ленте 0; остаются скрытыми 870 помеченных гейтом (причины
   вида «Новость о вводе ветропарка…»), 106 трекинговых копий РБК, 56 с тем же телом (Новатэк 47 —
   варианты страниц списка), 11 двойников убранного гейтом (Новатэк 10, Губкин 1), 4 с занятым ключом
   (TechnipFMC). Все 308 уже прошли ИИ (149 релевантны) — повторной оплаты нет; в окне сентября 56,
   из них релевантных 12.
3. `--apply` — в том же окне. Если в выводе есть «ДУБЛЬ В ЛЕНТЕ» — другое написание статьи успело
   вставиться после выката: ключ у старой строки не меняется, решить вручную (спрятать одну копию).
4. Первый цикл после выката вставит то, что терялось с 14.09: EIA 3, Минэнерго 15, Губкин 45 статей
   (+ релизы Лукойла/Новатэка) — залп небольшой, гейт ~70 статей.

Пока восстановление не прогнано, видимые статьи этих сайтов держат старый ключ: другое написание уже
собранной статьи (схема, хвост) может пройти рубеж по ключу — у RSS тело на вставке — анонс, а у старой
строки уже полный текст, так что рубеж по телу его не поймает. Поэтому шаги 1–3 — в одном окне.

## ИНЦИДЕНТ — мой, 25.09 05:56 UTC

Гасил свою браузерную пробу (запустил за минуту до указания владельца «не лезь») «деревом процессов»,
посчитанным в awk. `if (a[pp[x]])` в awk **создаёт** ключ, и `for (x in a)` выдал все родительские PID
хоста (0, 1, dockerd, containerd-shim, postgres). `kill -TERM` успел дойти до главного процесса
Postgres агентного контура — `oiltech_agents_pg`: в его логе 05:56:29.857 `received smart shutdown
request`, остановка чистая (контрольная точка записана), Docker поднял его за ~1,2 с, восстановление
после сбоя не понадобилось; `oiltech_agents_app` здоров, ошибок в логе нет. Следующим аргументом был
`0` — своя группа процессов, шелл умер, остальные PID из списка сигнала не получили (время работы
dockerd, `oiltech_pg`, планировщика, sshd не изменилось — проверено). Перед этим `pkill -f "<строка>"`
убил мою же SSH-сессию: строка была и в её команде. Это зона Германа и действие без «да» владельца.
**Правило:** на сервере убивать только явный PID после `ps -o cmd= -p PID`; никаких вычисляемых
списков, `pkill -f` и `kill 0`.

## Ложные версии — чтобы не повторять

1. **«Синхронный обрыв = регресс 18–19.09».** Дата последней статьи испорчена пересбором: у редких
   источников «последнее» — это старьё, вставленное 18.09. Проверять не дату последней статьи, а дату
   публикации того, что вставилось, и есть ли на сайте свежее, что не вставляется.
2. **«`last_parsed_at` свежий — источник опрашивается».** 25.09 он у ~60 источников стоял на 24.09 08:21:
   сбор висел 20,5 ч.
3. **Короткое замыкание по `last_listing_hash`** — его нет с июня (adf7a14); хэш пишется только для
   диагностики.
4. **Моя оценка «зомби chrome не срочны, `pid_max` 4 194 304».** Предел — у cgroup `pids.max` = 2315,
   зомби его и съели (разбор сессии зависания).
