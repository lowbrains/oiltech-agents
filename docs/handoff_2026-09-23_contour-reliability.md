Решения, которые принял я и которые стоит проверить глазами владельца:

1. **Частичный итог при остановке.** «Для уже записанных статей ИИ повторно не вызывается» выполнимо
   только так: воркер отдаёт сделанное (`partial`), ядро пишет его как при `complete` и вычитает из задачи
   (явный список — без обработанных, пакет «N статей» — N уменьшается). Сбор и документ частичного
   итога не отдают — возвращаются целиком (сбор ИИ не зовёт; итог документа — одна карточка).
2. **Замок на всё время жизни планировщика, а не на цикл.** С замком на цикл два экземпляра шли бы по
   очереди — без наложения, но со сбором и постановкой ИИ вдвое чаще, то есть тот же дубль 21.09.
3. **Схема при выкате — только явно.** Если `schema.sql` изменился между выкаченным и выкатываемым
   кодом, `deploy-core.sh` требует `--schema` или `--no-schema` и без выбора отказывает до сборки.
   `init-db` — не только CREATE/ALTER (моя ошибка в первой версии, поймана ревью): одна транзакция с
   бэкфиллами по всей `articles`, а `ADD COLUMN IF NOT EXISTS` берёт эксклюзивный замок даже на
   существующую колонку — на время прогона стоят лента и выдача задач NL. Для новой таблицы проще
   создать её вручную и выкатить с `--no-schema`.
4. **Сроки остановки:** 30 с на завершение + 60 с на шаг + 15 с на отчёт → `stop_grace_period: 120s`.
   Тест сверяет compose с `config.py`.

## Ловушки и ложные версии

- **Мой ложный тезис «`init-db` — только идемпотентные CREATE/ALTER».** В `schema.sql` есть UPDATE,
  INSERT и DELETE, файл идёт одной транзакцией, `ADD COLUMN IF NOT EXISTS` берёт эксклюзивный замок и на
  существующую колонку (ревью проверило на локальной базе). «Раньше шло при каждом `up`» — да, но тогда
  стек стоял целиком.
- **Часы ВМ colima спешат и раз в минуту подводятся назад (~200 мс).** Тест «ядро не выдало задачу» падал
  2 раза из 25: только что созданная задача была «из будущего». Оба сбоя ровно через 60 с. Продукт это не
  задевает; тесты повторяют `claim` до 2 с.
- **macOS `/bin/sh` (bash 3.2) при `LC_CTYPE=C.UTF-8` считает байт `»` частью имени переменной:**
  `"«$svc»"` → `svc\xc2: unbound variable`. В скриптах — `${svc}`.
- **`python -m` берёт код из рабочего каталога процесса, а не из `PYTHONPATH`;** `sitecustomize`
  грузится раньше, чем `-m` добавит каталог. Проверять «старый воркер против нового ядра» — только
  с `cwd` старой копии.
- Шаг планировщика живёт в своей группе процессов: после `kill -9` обёртки он сиротой держит pipe stdout
  открытым, и чтение вывода висит. В тестах вывод — в файл.
- Локально нет плагина `docker compose`; есть `docker-compose` 5.1.4 из Homebrew.
