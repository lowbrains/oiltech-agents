## Решения владельца (21–23.09)

- Радар и агент источников — зона Германа. **Он делает радар и только радар.**
- **Механики, которыми радар пользуется, приходят из нашего кода:** парсинг, скоринг (тот, что виден
  в карточке радара), теги, перевод. Дублировать их в агентном слое не нужно.
- Парсинг MVP-1 пока остаётся основным потоком бизнес-сигналов.
- Скрещиваем контуры с обновлением контейнеров. Главное — архитектура: задачи многопоточные, не
  ломаются, не сбиваются, РФ↔NL работает без сбоев.
- Архивное (пример — «Аналитика для БРБ») прячем в коде, контейнерах и интерфейсе.
- **Окно месяца — правило показа, одинаковое для всех ролей.** Никаких исключений для админа.
- **Из архива отмечать статьи «в дайджест» нельзя.** Для этого и сделан зазор в 5 дней: выпуск
  собирается в первые дни следующего месяца, пока прошлый месяц ещё виден.
- **Копии бэкапов остаются на том же сервере** — вопрос закрыт, отдельного выноса не делаем.

## Сессия B — окно месяца и архивные модули (папка `oiltech-digest`, ветка `feat/monthly-window`)

  - дата периода — `COALESCE(a.published_at, a.collected_at)`, как в `digest_candidates`;

## Сессия C — надёжность контура (папка `oiltech-digest`, ветка `feat/contour-reliability`)

**Цель:** задачи не дублируются, не теряются при выкате и не висят; РФ и NL сами сообщают о
расхождении. Пункты — по убыванию пользы.

1. **Мягкая остановка воркера.** Сейчас обработчика SIGTERM нет и `stop_grace_period` не задан.
   - по SIGTERM воркер перестаёт брать задачи и даёт текущим N секунд, чтобы закончить;
   - остальные сразу возвращаются в очередь новым вызовом release: статус queued, аренда снята,
     попытка не списывается, резерв статей снят или переиспользован;
   - `stop_grace_period` в compose — под N;
   - тест: SIGTERM посреди задачи → задача снова в очереди за секунды, а не через 600 с; для уже
     записанных статей ИИ повторно не вызывается.
2. **Один планировщик.**
   - `pg_try_advisory_lock` держится на весь цикл `docker-scheduler.sh`; второй экземпляр пишет
     строку в лог и ждёт;
   - профиль `pipeline` для `tasks`, `worker`, `playwright-worker`, `scheduler` — как в агентном
     репозитории;
   - тест: два процесса, шаги выполняет только один.
3. **Контракт версий.**
   - при `claim` воркер шлёт `X-Worker-Build` (git SHA, вшивается при сборке) и `X-Worker-Contract`
     (целое);
   - ядро хранит последнее значение каждого потребителя;
   - `check-lanes` и экран обслуживания показывают версии и тревогу `contract_mismatch`;
   - тест: воркер со старым контрактом вызывает тревогу.
4. **Пауза при пустой очереди:** 3 → 6 → … → 30 с, на первой задаче сбрасывается. Замер до и после;
   21.09 было 582 `claim` за 5 минут простоя.
5. **Скрипты выката.**
   - `scripts/deploy-core.sh <сервисы…>`: fetch и reset; отказ при живых ИИ-арендах без `--force`;
     сборка и `up -d --no-deps` только названных сервисов; ожидание health; `check-lanes`;
   - `scripts/deploy-nl.sh` для владельца: воркеры пересобираются по одному, с мягкой остановкой из
     п. 1; в конце — версии потребителей из ядра.

**Не трогать:** полосу `external-agents` (её делает A) и границу Германа.
**Выкат:** ядро на РФ; NL — готовыми командами для владельца.
**Готово, когда:**
- тесты зелёные;
- после пересборки NL нет задач `running` с мёртвой арендой;
- `check-lanes` показывает версии всех четырёх потребителей;
- в простое не больше ~60 `claim` за 5 минут.

## Сессия F — экраны по документу заказчика (папка `oiltech-digest`, ветка `feat/viktor-screens`)

**Цель:** закрыть правки из документа «Главная страница», которые относятся к нашему коду. Радар не
трогать. Выкат — на РФ после B и C.

1. **Источники.**
   - Найти и убрать расхождение счётчиков: вверху 133, в каталоге 173. Сначала замер — какие
     источники не попадают в счётчик и почему, потом правка.
   - Подписи: «Всего источников / Без материалов / Требуют внимания / Работают штатно / Отключены».
   - Экран — таблицей: источник, тип, состояние, последняя загрузка, материалов за 30 дней, проблема.
2. **Теги.** По умолчанию свёрнуты; «Родительский тег» → «Направление»; «+ Подтег» → «+ Добавить

3. **Перевод.** Замечания заказчика: «спудрил вертикальную скважину», «granular». Прогнать разбор
   терминологии (`list_article_texts_for_terminology_audit` и команда аудита), показать долю

**Готово, когда:** счётчик источников сходится с каталогом (число сверено запросом), экраны
соответствуют документу, тесты и фронт зелёные, на свежих статьях термины из замечаний переведены
правильно.

## Сессия G — профили скоринга: бизнес и технологический радар (после A и D)

**Цель:** два набора критериев вместо одного, переключаемые вкладками, с весами заказчика.

- Бизнес-сигналы: стратегическая значимость 30, бизнес-эффект 25, рыночная возможность 20,
  практическая применимость 15, достоверность и актуальность 10.
- Технологический радар: ценность для нефтесервиса 30, технологическая новизна 25, зрелость и
  доказательность 20, переносимость 15, свежесть 10.

Почему после слияния: оценка в карточке радара должна считаться **нашим** кодом, а это возможно
только в объединённом контуре. Перед реализацией — короткое решение (ADR): где живёт профиль, как
выбирается для статьи и сигнала, что происходит со старыми баллами. Эталон для проверки — вкладка
«Сентябрь_2026» из таблицы заказчика.
